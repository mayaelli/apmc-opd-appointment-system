# Government-grade OPD appointment system with institutional design and booking workflow

The frontend implements a 4-step appointment booking system for Amai Pakpak Medical Center's Outpatient Department. The interface adopts a formal government portal aesthetic with slate-900 header, emerald-600 accents, Arial typography, and structured institutional styling. The booking flow enforces a 2-slot-per-30-minute capacity limit, blocks weekends and holidays, requires category-specific intake forms, and generates a digital queue ticket. Navigation guards prevent data loss, and a 10-minute inactivity timer protects against abandoned sessions.

**Watch for:** TypeScript compilation error in app/layout.tsx (confirmed) — `LayoutProps<"/">` is not a valid Next.js type. Metadata values are placeholder defaults. The PhilHealth office assignment logic doesn't match the office selector implementation. The slot capacity enforcement is simulated via hash function, not backed by real state.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The layout adopts a fixed 1/3 left sidebar with progress tracker and 2/3 right workspace for the booking flow. The header follows government portal patterns with an emergency notification strip, deep slate background, emerald border accent, and Republic badge styling. The footer maintains the same institutional slate-800/emerald-600 palette with three-column structure.

The booking state machine enforces linear progression through 4 steps with per-step navigation guards that prompt on data loss. Step 1 selects from 3 consultation categories, each enforcing different intake forms in Step 3. Step 2 presents a Mon–Fri calendar (weekends removed from grid), a holiday blocker using hardcoded 2025–2026 Philippine holidays, and an 18-slot time picker (8:00 AM – 4:30 PM in 30-minute increments) with simulated capacity tracking. Step 3 renders conditional forms: New Check-up requires age/sex/chiefComplaint, Follow-up requires previousDoctorOrDepartment/purpose, PhilHealth Yakap requires philhealthPin/serviceType. Step 4 displays a screenshot-optimized ticket with queue ID (format: `APMC-{CODE}-{YYYYMMDD}-{4-digit-random}`), patient name, office, date/time, and mandatory arrival policy warning.

The 10-minute timeout starts on Step 1 and shows a 60-second countdown modal at 9 minutes. Browser navigation guards use `beforeunload` for refresh/close protection. TypeScript is strict-mode enabled with path aliases. Tailwind 4 is configured inline via `@theme`. All images reference the Amai Pakpak seal from `/public/`.

The implementation has one blocking TypeScript error: `LayoutProps<"/">` is not exported by Next.js 16. The office selector in Step 2 shows all 9 clinical departments for non-PhilHealth categories but doesn't enforce PhilHealth-only office assignment in the ticket. Slot capacity is simulated using a deterministic hash of the selected date, not real booking state.

## TypeScript error in root layout prevents compilation

`app/layout.tsx` declares the `children` prop as `LayoutProps<"/">`, which is not exported by Next.js. The build will fail with "Cannot find name 'LayoutProps'". The correct type for Next.js 16 App Router layouts is `{ children: React.ReactNode }` or the explicit `Readonly<{ children: React.ReactNode }>`. The generic `LayoutProps<"/">` syntax does not exist in the framework.

The fix is straightforward:

```typescript
export default function RootLayout({ children }: { children: React.ReactNode }) {
```

This is a **confirmed** blocking issue — the code cannot compile without this change.

## Metadata defaults are placeholder values

The `app/layout.tsx` file exports metadata with title "Create Next App" and description "Generated by create next app". These are the defaults from `create-next-app` scaffolding. The production app should use:

```typescript
export const metadata: Metadata = {
  title: "APMC OPD Appointment System",
  description: "Official online appointment and queue management system for Amai Pakpak Medical Center Outpatient Department",
};
```

This is a **confirmed** issue but low severity — the app functions correctly, but the browser tab and search engine results display generic placeholder text.

## 10-minute inactivity timeout with 60-second warning

The timeout starts on Step 1–3 and shows a 60-second countdown modal at 9 minutes. User activity (mousemove, keydown, click, scroll, touchstart) resets the timers **unless the warning modal is already visible**. Once the warning appears, activity does not dismiss it — the user must explicitly click "Continue Session". This prevents accidental dismissal.

The timeout does not persist on the ticket page (Step 4) because appointments are considered complete at that stage.

---

## Mon–Fri calendar with weekend removal and holiday blocking

`SchedulePickerView` builds a calendar grid with **only 5 columns** (Mon–Fri). Weekend dates are excluded from the grid entirely, not just disabled. Past dates are disabled via `jsDate < today` check.

The holiday blocker uses a `Set<string>` of hardcoded dates in YYYY-MM-DD format, covering 2025 and 2026 Philippine public holidays. Dates in this set are rendered with gray background and a small red dot indicator. The `handleDateClick` function exits early if `isHoliday` is true.

---

## 30-minute slot capacity enforcement via simulated hash

The slot picker shows 18 slots from 08:00 to 16:30. Capacity tracking is **simulated** via a hash function that computes `hash % 18`, `(hash * 7) % 18`, and `(hash * 13) % 18` to mark 2–3 slots as full for any given date, deterministically.

**Gap**: Two users booking the same date/slot will both succeed because no shared state exists. The hash function produces the same result on every page load for the same date, so refreshing doesn't change which slots appear full, but the simulation doesn't track actual bookings. A real implementation requires backend state or at minimum a shared client-side store (e.g., localStorage with collision detection, though that still wouldn't work across devices).

---

## Conditional intake forms enforce category-specific data requirements

`PatientDetailsView` renders one of three sub-forms based on `category`:

- **NewCheckupForm**: fullName, age, sex, phone, chiefComplaint (textarea, 300 char limit)
- **FollowUpForm**: fullName, phone, previousDoctorOrDepartment, purpose (textarea, 300 char limit)
- **PhilHealthYakapForm**: fullName, phone, philhealthPin, serviceType (dropdown with 6 options)

Each form uses `useMemo` to compute `isValid` from trimmed field presence. The "Next: Review Ticket" button is disabled if `!isValid`.

---

## Queue ID generation embeds category code, date, and random suffix

The `generateQueueId` function constructs `APMC-{CODE}-{YYYYMMDD}-{4-digit-random}` where CODE is `NCC` (New Check-up), `FUC` (Follow-up), or `PHY` (PhilHealth Yakap).

**Off-by-one bug**: The random part is `Math.floor(Math.random() * 9999 + 1)`, which produces values 1–10000. If the value is 10000, `.padStart(4, '0')` will not truncate it, resulting in a 5-digit suffix. The fix is `Math.floor(Math.random() * 9999) + 1` to ensure range 1–9999.

---

## PhilHealth category restricts office selector but ticket doesn't enforce mapping

`SchedulePickerView` shows only "PhilHealth Yakap Clinic" in the dropdown when `category === 'philhealth-yakap'`. The ticket displays `scheduleData.office`, which will be correct if the user follows the flow. But if state is manipulated (React DevTools, restored session), the ticket could show a mismatch.

If the requirement is "PhilHealth appointments must always display PhilHealth Yakap Clinic regardless of stored state", the ticket should derive the office from the category. If trusting the flow is acceptable, no change is needed.



---

## Browser navigation guard prevents data loss

The `beforeunload` listener in `booking/page.tsx` prompts "Leave site? Changes you made may not be saved" if `hasUnsavedChanges` is true (Steps 1–3 with data). Step 4 disables the guard.

**No back-button guard for in-page navigation** — the `hasUnsavedChanges` flag only protects against browser close/refresh. In-page back navigation (Step 2 → 1, Step 3 → 2) is handled separately via `window.confirm()`. The user cannot use the browser back button to navigate between steps because the URL doesn't change (all steps are rendered in `/booking`). If the URL structure changes in the future, this guard would need to be extended with Next.js router events.











---

## No test coverage

No test files exist in the repository. The `package.json` has no test runner configured. For a production government system handling patient appointment data, the absence of tests is a risk. Critical paths to test:

- Queue ID generation uniqueness and format
- Slot capacity enforcement (when real state is added)
- Navigation guard triggers on unsaved changes
- Timeout modal appears at 9 minutes
- Conditional form validation per category
- Holiday and weekend blocking
- Date/time formatting in ticket

The review does not flag this as blocking (the brief did not require tests), but production deployment should include at minimum integration tests for the booking flow and unit tests for the queue ID and calendar logic.
